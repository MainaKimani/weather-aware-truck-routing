# Deploying

The hosted app runs on free tiers:

| Part | Service | Free tier used |
|---|---|---|
| Frontend, and the one origin the browser sees | Vercel (Hobby) | Static build; rewrites `/api/*` to the API |
| API (Django, gunicorn, Docker) | Render (free web service) | 750 instance hours a month, 512 MB, sleeps after 15 min idle |
| Postgres | Neon (free) | 0.5 GB, 100 compute-hours a month, sleeps after 5 min idle |
| Redis (forecast cache, rate limits, Open-Meteo budget) | Upstash (free) | 500K commands and 256 MB a month |
| Daily retention purge, demo seed | GitHub Actions (`ops.yml`) | Render's free plan has no scheduled jobs |
| Keeping the API awake | An uptime pinger, e.g. cron-job.org | Every 10 minutes during the review window |

Everything sits in US East: Render `virginia`, Neon `aws-us-east-1`, Upstash `us-east-1`, and
Vercel's default `iad1`.

```
browser ──https──▶ Vercel ──/api/* rewrite──▶ Render (Django) ──▶ Neon Postgres
                     │                              └──────────▶ Upstash Redis
                     └── everything else: the built SPA
```

The browser only ever talks to the Vercel domain, so session and CSRF cookies are first-party
and no CORS is configured (RFC §3.2, §12). The Django admin is reached on Render's own domain.

## Order of setup

The Render service's name sets its URL, which `frontend/vercel.json` points at, and Vercel's
URL goes into Render's settings. So: databases, then Render, then Vercel, then back to Render
for the Vercel host.

### 1. Neon (Postgres)

1. Create a project in region **AWS US East 1 (N. Virginia)**, Postgres 16 or later.
2. Copy the **direct** connection string (the host without `-pooler`). Django keeps persistent
   connections (`CONN_MAX_AGE`), which a transaction pooler doesn't suit.
3. Make sure it ends in `?sslmode=require`. This is `DATABASE_URL`.

### 2. Upstash (Redis)

1. Create a Redis database in **us-east-1**, with TLS on (the default).
2. Copy the `rediss://default:<password>@<host>:6379` URL. This is `REDIS_URL`.
3. Leave eviction on: everything in Redis is a cache or a short-lived counter, and losing it
   costs at worst a refetch or a 429, never a bill. The HERE monthly budget is in Postgres.

### 3. Render (API)

1. **New > Blueprint**, pick this repository. Render reads `render.yaml` and proposes the
   `weather-aware-truck-routing-api` service (Docker, free plan, `backend/Dockerfile`).
2. Fill in the variables it asks for:

   | Variable | Value |
   |---|---|
   | `DJANGO_ALLOWED_HOSTS` | the Vercel host, e.g. `weather-aware-truck-routing.vercel.app` (fill in after step 4; use a placeholder for now) |
   | `CSRF_TRUSTED_ORIGINS` | `https://<vercel host>,https://weather-aware-truck-routing-api-xnow.onrender.com` |
   | `DATABASE_URL` | from Neon |
   | `REDIS_URL` | from Upstash |
   | `HERE_API_KEY` | the HERE key |
   | `DEMO_PASSWORD` | a password for the reviewer's demo account |

   `DJANGO_SECRET_KEY` is generated by Render. `NUM_PROXIES=2` and `WEB_CONCURRENCY=2` come
   from the blueprint. Render's own hostname is allowed automatically.
3. Render adds a suffix to the URL when the name is taken; this service is at
   `weather-aware-truck-routing-api-xnow.onrender.com`. If it ever moves, update the
   destination in `frontend/vercel.json`, the CSRF origin and the pinger to match.
4. The first deploy builds the image and runs the migrations on start. Check:
   - `https://weather-aware-truck-routing-api-xnow.onrender.com/healthz` → `{"status": "ok"}`
   - `https://weather-aware-truck-routing-api-xnow.onrender.com/readyz` → every check `ok`; this one
     touches Postgres and Redis, so it proves both connection strings.

### 4. Vercel (frontend)

1. **Add New > Project**, import this repository, set **Root Directory** to `frontend`. Vercel
   picks up `frontend/vercel.json` (Vite, `npm run build`, `dist`, and the rewrites).
2. Deploy, and note the production host (`<project>.vercel.app`).
3. Back in Render, set `DJANGO_ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS` to the real host and
   redeploy.

### 5. GitHub Actions (purge and demo seed)

1. In the repository's **Settings > Secrets and variables > Actions**, add `DATABASE_URL` (the
   same Neon string) and `DEMO_PASSWORD` (the same as Render's).
2. **Actions > Ops > Run workflow**, command `seed_demo`: creates or resets the demo account
   and its four trips.
3. `purge_trips` then runs daily at 04:17 UTC. GitHub pauses scheduled workflows after 60 days
   without repository activity; re-enable it from the Actions tab if that happens.

### 6. Keeping the API awake

Render's free service sleeps after 15 minutes without requests and takes about a minute to
wake. During the review window, point an uptime pinger (cron-job.org, UptimeRobot, …) at

```
https://weather-aware-truck-routing-api-xnow.onrender.com/healthz
```

every 10 minutes. One always-on service uses about 730 of the 750 free hours a month.

Ping `/healthz`, **not** `/readyz`: `/healthz` touches neither database, so Neon can still
sleep between real requests (it wakes in under a second). Pinging `/readyz` every 10 minutes
would keep Neon awake around the clock, about 730 hours a month against a free 100.

## Checks after deploying

- From a clean browser profile, in Chrome and Safari: plan a trip on the Vercel URL, sign up,
  save the trip, sign out and in again. Safari catches cookie problems first.
- `NUM_PROXIES`: every request is logged as one JSON line with a `client` field, the address
  rate limits key on. In Render's logs it should be your own public address, not a Vercel or
  Render one. If it's a proxy's, adjust `NUM_PROXIES` (it is also allauth's
  `ALLAUTH_TRUSTED_PROXY_COUNT`).
- The Django admin at `https://weather-aware-truck-routing-api-xnow.onrender.com/admin/` shows
  **Provider usage**: HERE calls this month against the 3,600 budget. Render's free plan has
  no shell, so make the superuser from your machine against Neon:
  `cd backend && DATABASE_URL='<neon string>' uv run python manage.py createsuperuser`.

## Known limits of the free setup

- **Speed:** the free instance is 512 MB with a fraction of a CPU. Plans and heatmaps do real
  work (a heatmap classifies about 28,000 point-hours), so the hosted latency budgets in
  SPOT-92 may need a paid instance.
- **Cold start:** if the pinger stops, the first request waits about a minute for Render, and
  Neon adds under a second after its own 5-minute sleep.
- **Quotas:** HERE 4,000 calls a month per service (the app stops at 3,600), Open-Meteo 10,000
  forecast points a day (the app stops at 9,000), Upstash 500K commands a month.
